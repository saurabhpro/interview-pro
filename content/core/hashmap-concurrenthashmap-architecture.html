JDK 26 map architecture

Public guarantees and present OpenJDK implementation are different claims. Lead with the contract; use internals to explain the performance.

The shared hash-table core

spread = h ^ (h >>> 16)
index  = spread & (capacity - 1)       // capacity is a power of two

table[0]  null
table[1]  Node ──▶ Node                // ordinary collision chain
table[2]  TreeBin / TreeNode           // red-black tree for a large bin
table[3]  Node
MechanismWhy it exists
Hash spreadingMoves influence from high hash bits into low bits used by the mask.
Power-of-two capacityUses a mask instead of modulo and makes resize splitting cheap.
List → tree at 8Bounds pathological collision search; treeification requires table capacity ≥ 64.
Tree → list around 6Avoids paying the larger tree-node cost for a small bin.

HashMap

Read: calculate index → test first node → traverse list or tree → compare stored hash and equals.

Write: insert in empty bin, replace matching key, or append/tree insert. Resize when size exceeds the threshold.

Resize: capacity doubles. An old-bin entry either remains at index j or moves to j + oldCapacity, decided by hash & oldCapacity.

No synchronization and no visibility guarantee. Fail-fast iteration is best-effort bug detection, not concurrency control.

ConcurrentHashMap

get(key)
  volatile/atomic table read ──▶ list/tree traversal      // normally no lock

put(key, value)
  empty bin    ──▶ CAS new Node                           // no lock
  occupied bin ──▶ coordinate on that bin, revalidate,
                    then list/tree mutation               // not a map-wide lock
  MOVED node   ──▶ follow nextTable / help resize
Internal partRole
volatile Node[] tablePublishes the current table safely.
Node(hash, key, volatile val, volatile next)Immutable identity plus visible value/link updates.
ForwardingNodeMarks a migrated old bin and points operations to the new table.
TreeBinWraps the specialised red-black tree and coordinates tree readers/writers.
ReservationNodeTemporary placeholder for atomic compute-style operations.
baseCount + CounterCell[]Spreads count-update contention instead of creating one hot counter.

There are no operational segments. The old Segment shape survives only for serialization compatibility; concurrencyLevel is a sizing hint.

Selection and traps

NeedCorrect choice
Thread-confined mutable lookupHashMap
Shared concurrent per-key stateConcurrentHashMap with putIfAbsent, compute, merge or conditional replace
Invariant spanning keys/processesExternal lock, single owner, transaction or another authoritative store
  • get then put is not one atomic operation.
  • Do not perform slow I/O inside compute; contending updates for that bin/key can wait.
  • Do not use size() as transactional control while concurrent updates are active.
  • Use immutable keys: changing fields used by equals/hashCode makes a mapping practically unreachable.
  • ConcurrentHashMap rejects null keys and values so null can mean unambiguously “absent”.
